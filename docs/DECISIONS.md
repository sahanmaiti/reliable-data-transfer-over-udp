## Decision 1: Use a 32-bit (`u32`) Monotonically Increasing Sequence Number
* **Context**: Protocols can use small modular numbers (e.g., 0/1 for Stop-and-Wait, $0 \dots 2^k - 1$ for sliding windows) or large 32-bit linear integers.
* **Decision**: Use `u32` representing the 0-indexed packet chunk number.
* **Reason**: 
  * A 32-bit sequence space provides up to $4,294,967,295$ packets ($\approx 4 \text{ TB}$ at $1024$ bytes/packet), preventing sequence number wraparound during university test transfers.
  * Makes debugging, logging, and metrics direct and human-readable without ambiguity.
  * In Selective Repeat, it makes window boundary checks simpler to reason about.

---

## Decision 2: 10-Byte Fixed Binary Header with Big-Endian Encoding
* **Context**: Need a standard header format shared across Stop-and-Wait, Go-Back-N, and Selective Repeat.
* **Decision**: A fixed 10-byte header: `seq_num (4B)` + `pkt_type (1B)` + `flags (1B)` + `payload_len (2B)` + `checksum (2B)`.
* **Reason**:
  * Adheres to standard network byte order (`Big-Endian`).
  * Easily serialized and deserialized using native slice methods (`to_be_bytes()` and `from_be_bytes()`) without heavy serialization dependencies (like Serde or bincode) in the core datapath.
  * Viva defensibility: every byte offset can be calculated and explained manually.

## Decision 3: Standard RFC 1071 16-bit Internet Checksum
* **Context**: Need an error-detecting code to catch synthetic bit errors generated by the channel emulator.
* **Decision**: Implement the 16-bit One's Complement sum (RFC 1071).
* **Reason**:
  * Standard networking algorithm (used by IPv4, TCP, and UDP).
  * Inexpensive to calculate in software and simple to demonstrate live during viva.
  * Checksum is zeroed out during calculation and restored afterwards.

---

## Decision 4: Synchronous State Machines Decoupled from Sockets
* **Context**: How to structure ARQ state logic for testability and clarity.
* **Decision**: Implement ARQ protocols as explicit state machines that take events/packets as inputs and return actions/packets as outputs, rather than embedding blocking socket calls inside the protocol loop.
* **Reason**:
  * Allows writing deterministic unit tests for every fault scenario (lost packet, delayed ACK, reordering, duplicate packet) without relying on real network timing or threads in tests.
  * Keeps the code clean, modular, and easy to explain during live modifications.
  * Integrates seamlessly with teammates' socket loops, timers, and channel emulator.
